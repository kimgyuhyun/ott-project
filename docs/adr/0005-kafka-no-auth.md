# 0005. Kafka 에 SASL 인증을 붙이지 않는다

- 상태: 채택 (조건부 — 아래 "재검토 조건")
- 관련: `docs/security.md`, [0004](0004-two-brokers.md)

## 배경

미들웨어 인증 상태가 셋 다 다르다.

| | 인증 | 어쩌다 그렇게 됐나 |
|---|---|---|
| Redis | 프로덕션만 | 명시적 결정(2026-07-18). base 는 무인증이고 `.prod.yml` 이 `--requirepass` 를 얹는다 |
| RabbitMQ | 항상 | 선택이 아니라 강제. 기본 `guest` 계정이 loopback 로그인만 허용해서, 컨테이너 간 접속을 하려면 계정을 만들 수밖에 없다 |
| Kafka | 없음 | 기본값이 무인증이라 그대로 뒀다 |

**셋의 상태가 다른 건 위협 모델이 달라서가 아니라 각 미들웨어의 기본값이 달라서다.**
이걸 방치하면 "왜 Kafka 만 무인증이냐"에 답할 수 없으므로, 의식적인 결정으로 못박는다.

## 결정

Kafka 는 세 리스너 모두 PLAINTEXT 로 두고 SASL 을 붙이지 않는다.

1차 방어선은 브로커 인증이 아니라 **망 분리**다. postgres / redis / kafka / rabbitmq 는 모두
`data` 네트워크에만 속하고, 여기에 도달할 수 있는 주체는 `app` 하나뿐이다. 프론트엔드는 웹
계층에만 있어 도달할 수 없다(2026-07-18 조치, 배포 스크립트가 자동 검증).

브로커 인증은 그 위에 얹는 **심층방어의 두 번째 겹**이다. Kafka 는 그 두 번째 겹이 없는
상태이고, 그것을 받아들인다.

## 대안

| 대안 | 판단 |
|---|---|
| SASL/SCRAM 적용 | **보류.** 아래 전제가 유효한 동안은 자격증명 관리·리스너 설정·장애 시 디버깅 비용만 늘어난다 |
| mTLS | **검토하지 않음.** 무인증을 유지한 건 위 전제를 근거로 한 것이고, mTLS 는 검토 대상에 올린 적이 없다 |

## 근거가 되는 전제

이 결정을 떠받치는 근거는 **하나뿐**이다.

> Kafka 는 인터넷과 분리돼 있고, 접근하는 주체는 백엔드뿐이다.

## 재검토 조건

위 전제가 깨지는 순간 이 ADR 은 무효다. 구체적으로 **아래 중 하나라도 발생하면 Kafka 인증을
함께 올린다.**

- 데이터 계층(`data` 네트워크)에 백엔드 외의 주체가 들어올 때
- 컨슈머를 별도 서비스/컨테이너로 분리할 때
- 브로커가 이 호스트 밖으로 나갈 때 (다중 호스트, 매니지드 Kafka 이전 등)

## 결과

- 무인증 상태가 "빠뜨린 것"이 아니라 "전제를 걸고 받아들인 것"으로 문서에 남는다
- 망 분리가 유일한 방어선이므로, 망 분리 검증이 배포 스크립트에서 빠지면 안 된다
- 참고: Redis 는 `REDIS_PASSWORD` 가 비면 `--requirepass ""` 로 **무인증에 조용히 떨어진다.**
  기존 동작을 깨지 않으려고 의도적으로 그렇게 뒀으니 `.env` 배포 시 값 존재를 확인해야 한다
