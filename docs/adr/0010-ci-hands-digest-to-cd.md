# 0010. 배포할 이미지는 CI 가 digest 로 지목하고 CD 는 그것만 받는다

- 상태: 채택 (2026-09-02)
- 관련: `.github/workflows/ci.yml`, `.github/workflows/cd.yml`,
  `.github/scripts/capture-image-digest.sh`, `docs/deployment.md`,
  [0001](0001-frontend-egress-block.md)

## 배경

2026-06 XMRig 재감염 대응으로 레지스트리를 Docker Hub 에서 GHCR 로 옮기면서
"digest 고정" 을 도입했다. 그런데 실제 구현은 이랬다.

1. CI 가 이미지를 `:<commit-sha>` 태그로 push 한다
2. CD 가 그 **태그로** pull 한다
3. CD 가 `docker inspect --format '{{index .RepoDigests 0}}'` 로 digest 를 뽑는다
4. 그 digest 로 배포한다

CI 는 자기가 스캔한 이미지가 무엇인지 CD 에 알려주지 않았다. 태그 문자열 하나만 넘어갔고,
태그→digest 해석은 CD 가 **pull 하는 그 순간에** 직접 했다. 그래서 이 고정이 실제로 막는
구간은 pull **이후**뿐이다 — 롤링 교체 중 태그가 바뀌어도 두 인스턴스가 같은 이미지로 뜬다.
CI 종료와 CD 의 pull 사이에 같은 태그가 덮어써지면, CD 는 그 이미지를 그대로 "고정" 해서
배포한다. `cd.yml` 상단 주석은 이걸 "태그 덮어쓰기 공격 무력화" 라고 적어 뒀다.

3번에도 별개의 결함이 있었다. `RepoDigests` 는 같은 이미지 ID 에 연결된 레포 이름마다 항목이
생기고 순서가 정해져 있지 않은데, 배포 마지막의 `docker tag $appImage ott-backend:clean` 이
짧은 이름을 그 목록에 넣는다(Docker Engine 28.4.0). 2026-09-02 배포 러너 실측:

```
[0] ott-backend@sha256:25b15ac...              <- 코드가 고르던 값
[1] ghcr.io/kimgyuhyun/ott-backend@sha256:25b15ac...
```

이미지 4개 전부 같은 상태였다. 즉 "digest 고정" 이 레지스트리 이름이 아니라 로컬 이름을
가리키고 있었고, `:clean` 태그가 언제 붙었는지에 따라 값이 두 형태 사이를 오갔다
(한 세대 전 이미지는 ghcr 쪽이 0번이었다).

## 결정

**배포할 이미지를 지목하는 주체를 CD 에서 CI 로 옮긴다.**

CI 가 push 직후 레지스트리 digest 를 캡처해 `image-digest-<이미지명>` 아티팩트로 올리고,
CD 는 그 아티팩트를 받아 `ghcr.io/<owner>/<name>@sha256:...` 로 pull 한다. CD 는 태그를
조립하지도, 태그를 digest 로 해석하지도 않는다. `docker inspect` 단계는 사라졌다.

같은 변경에서 Trivy 를 `docker push` **앞**으로 옮겼다. 이 순서가 아니면 CD 로 넘어가는
digest 가 "아직 스캔을 통과하지 않은 이미지" 를 가리키게 되고, 애초에 스캔이 push 뒤에
있으면 불량 이미지가 레지스트리에 남는다(PLATFORM 7절).

전달 수단이 아티팩트인 것은 선택이 아니라 제약이다. CD 는 `workflow_run` 으로 트리거되는데
**그 이벤트는 잡 output 을 나르지 않는다.** 워크플로 경계를 넘는 채널은 아티팩트와 이벤트
페이로드(`id`, `head_sha`, `conclusion`) 둘뿐이다.

## 대안

### 1. GHCR Immutable Tags 를 켠다

레지스트리에서 태그 덮어쓰기 자체를 금지하는 설정. 이 결정과 배타적이지 않고, 켜면 태그
경로를 쓰는 다른 곳(`docker-compose.e2e.yml`·`multi.yml` 의 기본값, 손으로 하는 pull)까지
덮인다.

채택하지 않은 이유: **불량 이미지가 `:sha` 를 먼저 점유하면 같은 커밋에서 재실행이
불가능해진다.** 빈 커밋을 쌓아 SHA 를 바꾸는 것 말고 우회가 없다. 이 파이프라인은 러너
사정으로 재실행이 실제로 필요한 종류다. 그리고 이 ADR 의 결정이 들어가면 **배포 경로에서는
태그가 아예 읽히지 않으므로** 남는 노출이 개발·실험 경로뿐이다. 같은 목적(불량 이미지를
레지스트리에 안 올리기)은 `build → scan → push` 재배치가 재실행 가능성을 잃지 않고 달성한다.

### 2. Cosign 으로 이미지에 서명한다

더 강한 보증이다. 이번 범위에서 제외했다 — 키 관리와 검증 지점이 늘어 별도 결정거리이고,
이 ADR 이 닫으려는 구멍(CI 와 CD 가 같은 이미지를 말하는지)은 서명 없이도 닫힌다.
서명은 "레지스트리와 CI 를 둘 다 믿지 못할 때" 의 계층이라 순서상 나중이다.

### 3. CD 가 레지스트리 API 로 태그→digest 를 조회한다

`docker inspect` 대신 레지스트리에 물어보는 안. `RepoDigests` 결함은 사라지지만
**해석 시점이 여전히 CD** 라 원래 구멍이 그대로다. 기각.

### 4. CI 가 `repository_dispatch` 로 CD 를 호출하며 digest 를 payload 에 넣는다

전달이 직접적이고 아티팩트 보존기간에 묶이지 않는다. 채택하지 않은 이유:
`repository_dispatch` 는 `GITHUB_TOKEN` 으로 못 쏘고 **PAT(장기 자격증명)가 필요하다.**
장기 자격증명을 없앤 것이 2026-06 사고 대응의 핵심 중 하나였다. 구멍 하나를 닫으려고
그때 없앤 것을 되살리는 거래는 하지 않는다.

### 5. 잡 output 으로 넘긴다

같은 워크플로 안(`e2e`)에서는 이렇게 한다. CD 로는 안 된다 — 위 "결정" 의 마지막 문단.
그리고 `proxies` 는 matrix 잡이라 **leg 끼리 output 이 서로 덮어써서** 이미지 2개의
digest 를 개별로 내보낼 수 없다. 아티팩트 이름에 `matrix.name` 을 넣어 우회한다.

## 무엇을 포기했는가

- **아티팩트 보존기간(기본 90일)이 롤백 한계가 된다.** `workflow_dispatch` 에 과거 CI 실행
  ID 를 넣어 그 릴리스로 되돌리는 경로는 아티팩트가 살아 있는 동안만 쓸 수 있다. 그보다
  오래된 릴리스는 revert 커밋 → CI → CD 로 되돌린다.
- **수동 배포에 API 조회가 한 번 늘었다.** `ci_run_id` 를 비우면 CD 가 main 의 최근 성공
  CI 실행을 조회하고, 그 커밋이 체크아웃된 HEAD 와 다르면 실패시킨다. 태그 폴백은 두지
  않았다 — 남기면 수동 배포 한 번으로 이 ADR 이 닫은 구간이 그대로 다시 열린다.
- **CI 가 한 번도 성공한 적 없는 상태에서는 수동 배포가 안 된다.** 검사를 통과한 적 없는
  이미지를 배포하는 경로라 막히는 것이 맞다고 봤다. 급할 때의 탈출구는 로컬
  `.\deploy-rolling.ps1`(`ott-backend:clean` 기본값)이 그대로 있다.

## 재검토 조건

- Cosign 서명을 도입할 때 — 그러면 "CI 가 지목한다" 대신 "서명이 지목한다" 가 되어 이
  ADR 의 전달 경로가 보조 수단으로 내려간다
- 90일보다 오래된 릴리스로 되돌려야 하는 일이 실제로 생길 때 — 아티팩트 대신 digest 를
  저장소에 커밋하는 안(릴리스 매니페스트)을 검토한다
- CD 를 `workflow_run` 이 아닌 방식으로 트리거하게 될 때 — 그러면 잡 output 이 열려
  아티팩트 경로가 불필요해질 수 있다
- GitHub 이 `workflow_run` 페이로드에 잡 output 을 싣기 시작할 때 (같은 이유)
