# 0004. 브로커를 Kafka 와 RabbitMQ 두 개 쓴다

- 상태: 채택
- 관련: `docs/messaging.md`, [0003](0003-sync-provisioning-async-side-effects.md), [0005](0005-kafka-no-auth.md)

## 배경

"본류에서 떼어내야 할 일"이 두 종류인데 요구하는 성질이 정반대였다.

| | 결제 성공 부수효과 | 정기결제 실패 재시도(dunning) |
|---|---|---|
| 필요한 것 | 순서 있는 스트림, 리플레이, 컨슈머 독립 추가 | 건별 지연 실행, 시간이 되면 정확히 한 번 |
| 대표 요구 | "이 이벤트를 여러 소비자에게 흘리고, 정산 버그 나면 되감아 재처리" | "3시간 뒤에 이 구독 건만 다시 청구" |

정기결제는 카드 한도 초과나 일시적 PG 장애로 실패하는데, 대부분 시간이 지나면 성공한다.
**즉시 재시도는 의미가 없다** — 한도 초과는 몇 시간 뒤에나 풀린다.

## 결정

성질에 맞는 브로커를 각각 쓴다.

- **Kafka**: 결제 부수효과 팬아웃. 아웃박스 테이블 + 파티션 + 오프셋. 파티션 키는 결제 PK 로
  잡아 같은 애그리거트의 순서를 보장한다
- **RabbitMQ**: 정기결제 재시도. 플러그인 없이 표준 기능만 쓴다 — **소비자가 없는 대기 큐에
  TTL 을 걸고, 만료된 메시지가 DLX 를 타고 실제 작업 큐로 떨어지는** 구조

대기 큐는 **지연 시간별로 분리**했다(3h / 24h). RabbitMQ 는 메시지 만료를 큐 머리에서만
검사하기 때문에, 한 큐에 TTL 을 섞으면 머리의 긴 TTL 이 뒤의 짧은 TTL 을 막는다
(head-of-line blocking). 3시간짜리가 24시간짜리 뒤에 서면 27시간 뒤에 나온다.

## 대안

| 대안 | 판단 |
|---|---|
| Kafka 하나로 통일 | **기각.** 건별 지연 실행이 어색하다. "특정 메시지만 3시간 뒤"를 오프셋 모델로 표현하기 어렵다 |
| RabbitMQ 하나로 통일 | **기각.** 리플레이(오프셋 되감기)와 컨슈머 그룹 독립 추가가 안 된다. 부수효과를 나중에 늘리려면 필요한 성질이다 |
| 재시도를 폴링 배치로 | **기각.** 주기마다 전체를 훑어야 하고, 지연 시간도 배치 주기만큼 부정확해진다 |
| 지연 단계를 한 큐에 TTL 섞어서 | **기각.** head-of-line blocking. 위 참조 |

## 결과

- **운영 대상이 둘로 늘었다.** 컨테이너, 모니터링, 장애 대응 지점이 각각 생긴다. 두 요구의
  성질 차이가 이 비용보다 크다고 판단한 것이다
- 지연 단계를 늘리려면 큐를 추가해야 한다 — **단계 수가 적을 때만 성립하는 트레이드오프**다
- 큐 인자(`x-message-ttl` 등)는 최초 선언 시 고정된다. 지연 값을 바꾸고 재배포해도 반영되지
  않고 인자 불일치로 선언이 실패한다. 기존 큐를 먼저 삭제해야 한다
- 재시도 처리 중 예외는 재큐잉하지 않고 폐기한다(무한 루프 방지). 대신 `nextBillingAt` 기준
  스윕 배치를 최후 안전망으로 둔다 — **메시지 큐를 유일한 진실로 삼지 않는다**
