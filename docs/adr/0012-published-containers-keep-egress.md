# 0012. 호스트 포트를 공개하는 컨테이너의 아웃바운드는 망 설정으로 막지 않는다

- 상태: 채택 (조건부 — Docker Desktop 에 있는 동안)
- 관련: `docker-compose.netlock.yml`, `docker-compose.monitoring.yml`, [0001](0001-frontend-egress-block.md)

## 배경

PLATFORM 3절은 인터넷 아웃바운드가 실제로 필요한 서비스만 아웃바운드 망에 붙이라고 한다.
2026-11-20 점검에서 이 조건을 어기는 컨테이너가 넷 있었다. 넷 다 아웃바운드가 필요해서가
아니라 **호스트 포트를 공개하려고** non-internal 망에 붙어 있다.

| 컨테이너 | 공개 포트 | 붙은 non-internal 망 | 아웃바운드가 필요한가 |
|---|---|---|---|
| nginx | 80, 443 (인터넷) | `egress` | 아니다. 업스트림은 전부 내부, resolver·OCSP 스테이플링 없음 |
| prometheus | 127.0.0.1:9090 | `monitoring` | 아니다 |
| loki | 127.0.0.1:3100 | `monitoring` | 아니다 |
| grafana | 127.0.0.1:3001 | `monitoring` | 아니다. 사용통계·업데이트 확인은 환경변수로 꺼져 있다 |

도커는 `internal: true` 망에만 붙은 컨테이너의 포트를 호스트로 공개하지 않는다. 그래서 공개가
필요한 컨테이너는 non-internal 망에 하나는 붙어야 하고, 그 망은 인터넷으로 나간다.

## 실측

리눅스 도커에서는 브리지 망의 NAT(`com.docker.network.bridge.enable_ip_masquerade=false`)를
끄면 포트 공개는 유지하면서 아웃바운드만 끊을 수 있다. 이 호스트(Docker Desktop, WSL2)에서도
되는지 2026-11-20 에 같은 이미지로 대조 실험을 했다.

| 망 | 127.0.0.1 포트 공개 | 컨테이너 → 1.1.1.1 |
|---|---|---|
| 일반 브리지 (대조군) | 200 | 열림 |
| NAT 를 끈 브리지 | 200 | **열림** |

NAT 를 꺼도 아웃바운드가 열려 있다. Docker Desktop 은 컨테이너 트래픽을 VM 밖에서 다시
내보내므로 브리지의 NAT 설정이 차단으로 이어지지 않는다(이 부분은 결과로 본 것이고 내부
구현은 확인하지 않았다).

## 결정

**네 컨테이너의 아웃바운드는 망 설정으로 막지 않는다.** 이 환경에서 망 설정만으로 막을 수단이 없다.

대신 **누가 이 컨테이너에 들어올 수 있는가**를 줄인다. 아웃바운드는 그 컨테이너가 먼저 뚫려야
의미가 생기기 때문이다.

| 컨테이너 | 들어올 수 있는 주체 (2026-11-20 이후) |
|---|---|
| nginx | 인터넷 전체 |
| prometheus, loki | 호스트 루프백, 그리고 `obs` 망의 앱 2대·alloy |
| grafana | 호스트 루프백 |

prometheus·loki 는 전에는 `default` 망에도 있어서 프론트엔드가 닿았다(실측: 프론트에서 loki
로그 조회 성공, 인증 없는 push 수락). 2026-06 에 두 번 뚫린 컨테이너가 바로 그 프론트엔드다.
그래서 같은 날 둘을 앱 전용 internal 망 `obs` 로 옮겼고, 배포 스크립트가 프론트 → loki·prometheus
차단을 매번 확인한다. 남는 진입 경로는 "호스트나 앱이 먼저 뚫린 경우"뿐이다.

nginx 는 인터넷에서 바로 들어올 수 있으므로 위험이 남는다. 지금 있는 방어는 하드닝(읽기 전용
루트, `cap_drop: ALL` 후 필요한 것만, no-new-privileges, 리소스 상한)이고, 이것은 피해를
줄일 뿐 아웃바운드를 막지 않는다.

## 대안

### 1. NAT 를 끈 브리지로 공개용 망을 따로 둔다

위 실측으로 효과가 없음을 확인했다.

### 2. prometheus·loki 의 공개 포트를 없애고 `obs` 에만 둔다

loki 의 3100 은 디버깅용이라 쓰는 곳이 없다. prometheus 의 9090 은 호스트의 경보 릴레이
(`security/ott-alert-relay.ps1`)가 쓴다. 릴레이를 `docker exec` 조회로 바꾸면 9090 도 뺄 수 있다.

채택하지 않은 이유: 둘 다 들어올 수 있는 주체가 이미 호스트 루프백과 앱뿐이라 줄어드는 위험이
작다. 반면 grafana 가 loki 를 조회하려면 grafana 를 `obs` 에 붙여야 하는데, grafana 는 포트
공개 때문에 아웃바운드가 열린 컨테이너다. 그런 컨테이너를 앱 전용 internal 망에 넣는 것은
`obs` 를 만든 목적과 반대다.

### 3. 호스트 방화벽의 아웃바운드 규칙

Docker Desktop 에서 컨테이너별로 구분되는 규칙을 걸 수 있는지는 검증하지 않았다. 백엔드의
아웃바운드(squid)는 열려 있어야 하므로, 컨테이너를 구분하지 못하는 규칙은 쓸 수 없다.

### 4. 리눅스 Docker Engine 으로 옮긴다

대안 1 이 그대로 동작하고, 필요하면 iptables `DOCKER-USER` 체인으로 컨테이너별 차단도 된다.
근본 해결은 이것이다. 단일 호스트 이전 작업이라 이 결정의 범위를 넘는다.

## 재검토 조건

- 리눅스 Docker Engine 으로 옮길 때 — 대안 1 을 다시 실측하고, 되면 이 ADR 을 대체한다
- prometheus·loki·grafana 중 하나가 호스트 루프백 밖(LAN, Tailscale 외 경로)으로 공개될 때
- `obs` 망에 앱·관측 스택이 아닌 컨테이너가 붙을 때
