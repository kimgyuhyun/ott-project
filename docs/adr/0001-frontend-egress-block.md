# 0001. 프론트엔드 컨테이너의 아웃바운드를 차단한다

- 상태: 채택 (2026-06)
- 관련: `docs/incident-2026-06.md`, `docs/security.md`, [0002](0002-rolling-deploy-sequential.md)

## 배경

2026-06 프론트엔드 컨테이너가 XMRig 채굴 멀웨어에 **두 차례** 감염됐다.

1차에는 이미지 공급망 감염으로 판단하고 클린 이미지 재빌드 + 컨테이너 하드닝(비root, 읽기전용
루트 파일시스템, `cap_drop: ALL`, `no-new-privileges`, digest 고정)으로 대응했다. 며칠 뒤 그
상태에서 같은 지갑·같은 풀·같은 파일명으로 **재발했다.**

2차 조사에서 실행 이미지를 클린 이미지와 바이트 단위로 대조해 이미지가 원인이 아님을 확인했고,
1차 포렌식 자료를 다시 보니 1차도 런타임 주입이었다 — 컨테이너 시작 8.5시간 뒤에 파일이 생겼고,
컨테이너 stdout 에 앱 프로세스가 드로퍼를 실행한 로그(`wget ... |sh`)가 남아 있었다.

**익스플로잇 체인은 로그 소실로 끝내 규명하지 못했다.** 즉 "어디로 들어왔는지 모르는 상태에서
서비스를 지켜야 한다"가 이 결정의 전제 조건이었다.

## 결정

침입 자체를 막는 대신 **침입의 가치를 없앤다.** 프론트엔드를 인터넷으로 나갈 수 없는 망에
격리하고, 인터넷이 실제로 필요한 백엔드만 egress 망에 연결한다 (`docker-compose.netlock.yml`).

크립토재킹은 채굴 풀에 연결돼야 성립한다. 아웃바운드가 막히면 드로퍼 다운로드부터 실패하고
공격자 수익이 0 이 된다. **침투 벡터를 몰라도 유효한 방어**라서 골랐다.

## 대안

| 대안 | 판단 |
|---|---|
| 클린 이미지 재빌드 (1차 대응) | **기각.** 원인이 이미지가 아니었다. 증상이 사라진 건 재빌드가 아니라 컨테이너를 새로 띄웠기 때문이고, 그래서 며칠 뒤 재발했다 |
| 컨테이너 하드닝만 유지 | **불충분.** 1·2차 비교가 실측이다 — 드롭 위치를 `/app/public` 에서 `/tmp` 로 밀어내고 root 권한을 뺏었지만 침입은 그대로 성립했다. 피해 감소지 예방이 아니다 |
| 취약점 패치 (Next.js 업그레이드) | **병행하되 단독으로는 불충분.** 알려진 취약점만 닫는다. 벡터를 규명하지 못한 상태에서 이것만 믿을 수 없었다 |

## 결과

- 채굴 프로세스 0개, HTTPS 200 복구, 프론트엔드 아웃바운드 차단 직접 확인. 이후 재발 없음
- **netlock 오버레이가 빠진 채 배포되면 아웃바운드가 다시 열린다.** 그래서 맨손
  `docker compose up` 을 금지하고 배포는 반드시 스크립트를 경유한다
- 하드닝 설정은 사람이 기억해서 붙이는 게 아니라 prod 오버라이드에 내재화해 CD 가 항상 강제한다
- 이 방어는 벡터가 아니라 **결과**를 막는 구조다. 같은 진입로가 열려 있을 가능성은 배제하지 못한다
- 단일 호스트 구성이라 호스트 자체가 침해되면 컨테이너 격리는 무의미하다
