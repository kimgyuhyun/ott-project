# 0003. 결제 확정과 구독 생성은 동기로, 부수효과만 이벤트로 분리한다

- 상태: 채택 (되돌린 결정)
- 관련: `docs/messaging.md`, [0004](0004-two-brokers.md)

## 배경

결제 성공 뒤에 일어나야 할 일이 여러 가지다 — 멤버십 구독 생성, 영수증 메일, 통계 집계, 추천
반영. 처음에는 이걸 전부 이벤트 리스너로 비동기 처리했다.

**그 결과 "결제는 `SUCCEEDED` 인데 구독은 미생성"인 상태가 발생했다.** 사용자 입장에서는 돈을
냈는데 서비스를 못 쓰는 상황이고, 결제 상태만 보면 정상이라 탐지도 늦다.

## 결정

**돈이 오가는 확정은 동기, 그 이후 파급효과는 이벤트로 분리한다.**

- 결제 확정(PG 재검증 → `SUCCEEDED` → 멤버십 구독 생성)은 하나의 동기 트랜잭션으로 처리한다
  (`PaymentCommandService.markSucceededAndProvision`)
- 결제 성공 "이후" 부수효과(영수증 메일, 통계, 추천)만 Kafka 로 비동기 분리한다
- 이벤트 발행은 같은 트랜잭션에서 `outbox_events` 에 INSERT 하고 폴링 발행기가 실어보낸다
  (Transactional Outbox — DB 커밋과 이벤트 발행 사이의 dual-write 문제 회피)

경계 기준은 **"이게 실패하면 사용자가 돈을 낸 대가를 못 받는가"** 다. 그렇다면 동기다.

## 대안

| 대안 | 판단 |
|---|---|
| 전부 비동기 (원래 구조) | **실제로 해봤고 기각.** 위 정합성 사고가 근거다 |
| 전부 동기 | **기각.** 메일 서버가 죽으면 결제 확정까지 같이 실패한다. 실패해도 되는 일이 실패하면 안 되는 일을 끌고 내려간다 |
| 아웃박스 없이 트랜잭션 커밋 후 직접 발행 | **기각.** 커밋과 발행 사이에 죽으면 이벤트가 유실된다. 반대로 발행 후 커밋 실패면 없는 결제의 이벤트가 나간다 |

## 결과

- 아웃박스 폴링 주기(2초)만큼 부수효과가 지연된다. 부수효과라서 허용 가능한 지연으로 봤다
- 아웃박스는 **발행 성공 후에만** PUBLISHED 로 마킹하므로 at-least-once 다. 중복 배달이
  전제되므로 컨슈머에 멱등 처리가 필수다 (`PaymentEventConsumer` + Redis `eventId`, TTL 7일)
- 재시도 후에도 실패한 이벤트는 `.DLT` 로 격리한다. 조용한 유실을 만들지 않기 위해서다
- 멱등 컨슈머 덕분에 오프셋을 되감아 리플레이해도 메일이 중복 발송되지 않는다
- 결제 확정 경로가 3개(결제창 콜백/웹훅/재조정 배치)라 `markSucceededAndProvision` 에
  멱등 가드를 둬서 정확히 1회로 수렴시킨다
