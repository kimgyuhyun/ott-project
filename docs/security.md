# 보안 설계

무엇을 왜 적용했는지만 적는다. 공개 저장소이므로 비밀값, 실제 호스트·IP, 우회에 직접 쓰일 수 있는
임계값이나 예외 조건은 적지 않는다. 그런 값은 `.env.enc` 와 각 설정 파일에만 둔다.

## 배경

2026-06 프론트엔드 컨테이너가 크립토마이너에 두 차례 감염됐다. 처음엔 이미지 감염으로 판단했으나
조사 결과 두 번 모두 **실행 중인 컨테이너 안으로 주입된 것**이었다. 이미지·호스트·레지스트리에서는
오염 증거를 찾지 못했고, 익스플로잇 체인은 로그 소실로 끝내 규명하지 못했다. 컨테이너 하드닝은
피해를 줄였을 뿐 침입 자체는 막지 못했다. 그래서 방어는 "침입을 100% 막는다"가 아니라 **침입해도
돈이 안 되게 만든다**는 방향으로 설계했다. 아래 항목 대부분이 그 결론에서 나왔다.
경위는 `docs/incident-2026-06.md`.

## 네트워크 격리 (netlock)

- 웹 계층과 데이터 계층 네트워크를 `internal` 로 두어 인터넷 아웃바운드를 끊는다
- 인터넷이 실제로 필요한 백엔드(OAuth·메일·결제·외부 API)만 별도 egress 네트워크에 연결
- 프론트엔드는 아웃바운드가 없다 → 감염돼도 채굴 풀·C2로 나가지 못해 무력화된다
- 프론트엔드는 데이터 계층에도 속하지 않는다 → 뚫려도 DB·브로커로 횡이동 불가
- 정의는 `docker-compose.netlock.yml`. **배포 시 이 파일이 빠지면 egress가 다시 열린다**

### 아웃바운드 목적지 허용목록 (2026-08-07)

망 분리는 아웃바운드가 필요 없는 서비스를 끊을 뿐, egress 망에 붙은 서비스의 목적지까지는
제한하지 못한다. 백엔드는 egress 망과 data 망에 동시에 있었으므로, 침해되면 DB를 읽어 임의의
목적지로 보내는 경로가 그대로 열려 있었다. 그래서 백엔드를 egress에서 빼고 프록시 전용
internal 망에 두었다.

- 백엔드의 HTTP/HTTPS 아웃바운드는 전부 포워드 프록시(squid)를 거친다. 기본 거부 + 목적지
  허용목록이고, 목록에 있는 것은 결제 게이트웨이·OAuth 세 곳의 토큰/사용자정보 엔드포인트·
  봇 방어 검증·외부 콘텐츠 API 두 곳뿐이다
- 브라우저 리다이렉트 주소나 브라우저가 직접 받아가는 이미지 호스트는 목록에 없다.
  백엔드가 소켓을 열지 않는 곳이기 때문이다
- HTTPS는 CONNECT의 평문 호스트명으로 판정한다. **TLS 복호화(ssl_bump)는 쓰지 않는다**
- 메일(SMTP)만 SOCKS5 프록시를 거친다. HTTP 프록시로는 나를 수 없고, SOCKS는 목적지
  호스트명을 그대로 전달해 STARTTLS 인증서 검증이 바뀌지 않는다. JVM 전역 SOCKS 설정은
  쓰지 않는다 — 그러면 DB·브로커 연결까지 SOCKS로 끌려간다
- 프록시는 `proxy`와 `egress` 두 망에만 속한다. `default`에 붙이면 프론트엔드가 프록시를 통해
  인터넷을 되찾고, `data`에 붙이면 프록시가 곧 DB 접근 경로가 된다
- 배선과 프록시 정의는 `docker-compose.netlock.yml` 한 파일에 있다. 프록시와 망 제약이 같이
  붙고 같이 빠져야 "프록시는 없는데 프록시로 나가라는 설정만 켜진" 상태가 안 생긴다
- 배포 스크립트가 인스턴스마다 다섯 가지를 확인한다: 허용 목적지가 프록시로 뚫리는지,
  비허용 목적지를 프록시가 거부하는지, 직접 아웃바운드가 막혔는지, 외부 DNS가 막혔는지,
  그리고 SMTP가 SOCKS로 뚫리면서 비허용 목적지는 거부되는지. 마지막 것이 없으면 앞의 넷이
  전부 HTTP 경로만 보게 되어, 메일 경로가 끊긴 채로 배포가 통과한다

**되돌리는 순서** (기능 장애가 허용목록 때문일 때)

1. `proxy/squid.conf`를 전부 허용으로 되돌리고 무중단 반영:
   `docker exec ott-egress-proxy squid -k reconfigure`
2. 그래도 안 되면 `docker-compose.netlock.yml`에서 app/app2를 `proxy` 대신 `egress`로 되돌린다
3. 이때 배포 스크립트의 새 검사 4개도 함께 되돌려야 배포가 통과한다 (검사는 직접 아웃바운드가
   **막혀 있을 것**을 요구하므로, 2번만 하면 배포가 실패한다)

프록시가 죽으면 백엔드의 외부 호출이 전부 죽는다. 결제·메일뿐 아니라 봇 방어 검증이
fail-closed라 로그인·회원가입까지 막힌다 — 프록시는 가용성 측면에서 백엔드와 같은 등급이다.

## 컨테이너·이미지

- 레지스트리는 GitHub Container Registry(비공개). 침해 이력이 있는 공개 Docker Hub 계정은 폐기
- 배포 대상은 **CI가 지목한다**. CI가 push 직후 레지스트리 digest를 캡처해 아티팩트로 넘기고,
  CD는 `@sha256:`으로만 pull한다 → 태그 덮어쓰기로 다른 이미지가 끼어들 수 없다.
  CD가 태그를 digest로 해석하던 때는 CI 종료와 CD의 pull 사이가 열려 있었다
  ([ADR 0010](adr/0010-ci-hands-digest-to-cd.md))
- 베이스 이미지도 digest로 고정. 베이스가 움직여도 빌드가 조용히 바뀌지 않고 Dependabot PR로 드러난다
- CI에서 Trivy 스캔. 패치가 나온 CRITICAL이 있으면 **push 전에** 실패시켜 불량 이미지가
  레지스트리에 올라가지도, 배포로 넘어가지도 못하게 한다
  (패치 없는 취약점으로는 막지 않는다 — 막아도 할 수 있는 조치가 없어 게이트만 무력화된다)
- 런타임에 불필요한 도구는 프로덕션 이미지에서 제거해 공격 표면을 줄인다
- 컨테이너는 비root 사용자로 실행

## 인증과 권한

- PostgreSQL은 용도별로 계정을 분리한다. 마이그레이션 계정과 런타임 계정의 권한이 다르며,
  런타임 계정은 스키마 변경 권한이 없다 (`security/postgres-least-privilege.sql`)

### 브로커·캐시 인증은 심층방어의 두 번째 겹

1차 방어선은 브로커 인증이 아니라 **망 분리**다. postgres/redis/kafka/rabbitmq는 모두 `data`
네트워크에만 속하고, 여기에 도달할 수 있는 주체는 `app` 하나뿐이다(프론트는 웹 계층에만 있어
도달 불가 — 2026-07-18 조치). 각 브로커의 인증 유무는 그 위에 얹는 두 번째 겹이고, 셋의 상태가
다른 건 위협 모델이 달라서가 아니라 **각 미들웨어의 기본값이 달라서**다.

| | 인증 | 왜 이렇게 됐나 |
|---|---|---|
| Redis | 프로덕션만 사용 | 명시적 결정(2026-07-18). base는 무인증, `.prod.yml`이 `--requirepass ${REDIS_PASSWORD}`를 얹는다 |
| RabbitMQ | 항상 사용 | 선택이 아니라 강제. 기본 `guest` 계정이 loopback 로그인만 허용해서, 컨테이너 간 접속을 하려면 계정을 만들 수밖에 없다 |
| Kafka | 사용 안 함 | 기본값이 무인증이라 그대로 뒀다. 세 리스너 모두 PLAINTEXT |

- Redis 인증은 `REDIS_PASSWORD`가 비면 `--requirepass ""`로 **무인증에 그대로 떨어진다**.
  기존 동작을 깨지 않으려고 의도적으로 그렇게 뒀으니, `.env` 배포 시 이 값이 있는지 확인할 것
- Kafka에 SASL을 붙이지 않은 근거는 "인터넷과 분리돼 있고 접근 주체가 백엔드뿐"이라는 전제
  하나뿐이다. 데이터 계층에 다른 주체가 들어오거나 브로커가 호스트 밖으로 나가면 이 전제가
  깨지고, 그때는 Kafka 인증을 함께 올려야 한다

## 애플리케이션

- **CSRF**: 토큰 방식 대신 Origin 검증 필터(`OriginValidationFilter`)를 쓴다. 공용 도메인을
  쓰는 환경이라 SameSite 쿠키만으로는 보호가 약해지기 때문. 문제 시 끌 수 있는 설정을 둔다
- **봇 방어**: 로그인 반복 실패 이후와 인증코드 발송에 Cloudflare Turnstile 검증
  (`TurnstileVerifier`). 정상 사용자는 대부분 마주치지 않는 위치에만 건다
- **보안 헤더 (CSP)**: CSP 는 프론트엔드 `frontend/next.config.ts` 의 `headers()` 한 곳에서만
  내려준다. nginx 에는 일부러 넣지 않는다 — 양쪽에서 만들면 한쪽이 다른 쪽을 통째로 덮어써서
  무엇이 차단됐는지 추적하기 어려워진다
- **보안 헤더 (나머지)**: HSTS, X-Frame-Options, X-Content-Type-Options, Referrer-Policy,
  Permissions-Policy 는 nginx 에서 적용한다. 같은 블록이 `nginx/nginx.prod.conf` 와
  `nginx/nginx.prod.ha.conf` 두 곳에 있으므로 **헤더를 바꿀 땐 반드시 둘을 같이 고친다**.
  무중단 롤링 배포는 ha.conf 를 쓰기 때문에, 한쪽만 고치면 배포 경로에 따라 헤더가 달라진다
- **레이트 리밋**: nginx `limit_req`
- **버전 노출 억제**: nginx `server_tokens off`. 버전이 보이면 스캐너가 그 버전에 걸리는
  알려진 취약점만 골라 시도할 수 있다. 패치를 대신하지는 못하고 표적 선정을 어렵게 하는
  정도의 효과다. 위 두 nginx 파일에 함께 둔다
- **스트리밍 보호**: HLS는 서명된 URL로만 접근 가능하며 서명 검증을 엣지에서 수행한다.
  원본 스토리지는 공개 접근을 차단해 우회 경로를 없앴다 (설계: `docs/streaming.md`)

## 비밀 관리

- 값의 단일 소스는 `.env.enc` (SOPS + age 로 암호화해 저장소에 커밋)
- 복호화 키는 CI/CD 비밀에만 있고, 배포 시점에 `.env` 를 만든다
- 평문 `.env` 는 저장소에 올리지 않는다. 사본이 여러 곳에 생기지 않는 것이 이 방식의 목적

## 호스트

- 외부 공개는 80/443 뿐
- SSH(22)는 닫혀 있고 배포는 self-hosted 러너를 통해서만 이뤄진다
- 개발 환경에서 DB·Redis는 루프백에만 바인딩한다
