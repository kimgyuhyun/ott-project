### 결과 1: nginx 경유 — 측정 실패

목표 부하를 만들지 못했다. **서버 문제가 아니라 레이트 리밋에 막힌 것**이다.

| 지표 | 값 |
|---|---|
| 실패율 | **72.70%** (38,058 / 52,349) |
| 로그인 실패율 | 77.27% (1,700 / 2,200) |
| 처리량 | 115.2 RPS (시도 기준) |

실패 응답은 전부 nginx 가 백엔드에 보내지 않고 돌려준 것이다. `docker logs ott-nginx` 의
`limiting requests` 기록이 38,059 건으로 k6 가 센 실패 38,058 건과 일치했다.

원인은 `limit_req` 가 `$binary_remote_addr` 기준이라 VU 500 명이 IP 한 개의 버킷(general 30 r/s)을
공유한 것. 실사용자 500 명이면 IP 가 흩어져 발생하지 않는다. 자세한 내용은 README 의 레이트 리밋 절.

이 구간의 지연 수치(p95 14ms 등)는 **리밋을 통과한 26% 에 대한 값이라 성능 지표로 쓸 수 없다.**

### 판정: 1500 VU 까지 꺾이지 않았다

포화점의 정의는 **처리량이 정체되는데 p95 만 급격히 올라가는 지점**이다. 둘 다 나타나지 않았다.

- 처리량은 VU 에 정비례했다. VU 1명당 RPS 가 0.278 / 0.276 / 0.274 / 0.277 / 0.278 로 계단 내내 평평하다.
  정체 구간이 없다 = 서버가 요청을 밀어내지 못한 순간이 없었다.
- p95 는 10ms 안팎에 머물렀다. 1500 VU 에서 12.86ms 로 올라갔지만 100 VU 의 11.69ms 와 같은 급이고,
  급격한 상승이 아니다. p99 만 18 → 29ms 로 조금 벌어졌다.
- 에러 0 건(163,117 요청 중 0), 로그인 실패 0 건(1,500 중 0).
- `iteration_duration` 중앙값 5.00s = 설계값 그대로. **이터레이션이 밀리지 않았다** — 밀리기 시작하면
  VU 가 다음 tick 을 제때 못 쏘므로 처리량 정체로 먼저 드러난다. 그 조짐이 없었다.

즉 **이 호스트에서는 1500 VU(동시 시청자 1500명, 416 RPS)까지 여유가 있다.** 목표 부하 500명의 3배다.

### 이 측정이 답하지 못하는 것

**한계를 찾지 못한 이유는 서버가 무한히 빨라서가 아니라, 이 부하 모델이 요청량을 스스로 제한하기 때문이다.**
VU 1명은 5초에 1 tick 이라는 고정 주기로 돌기 때문에(closed-loop) 서버가 아무리 빨라도 1500 VU 가
만들 수 있는 부하는 약 417 RPS 가 상한이다. 실제로 그 상한이 그대로 나왔다. 즉 이번에 확인한 것은
"416 RPS 까지는 확실히 여유"이지 "한계가 416 RPS"가 아니다.

진짜 포화점을 보려면 둘 중 하나가 필요하다.

| 방법 | 내용 |
|---|---|
| VU 를 더 올린다 | 3000 ~ 5000 VU. 계정 500개를 6~10 세션이 공유하게 된다 |
| open-loop 로 바꾼다 | `constant-arrival-rate` 로 목표 RPS 를 직접 지정. 서버가 느려져도 요청 발생률이 안 줄어 큐가 쌓이는 게 보인다 |

closed-loop 은 서버가 느려지면 부하도 같이 줄어들어 포화를 완만하게 감춘다. 한계를 정확히 재려면
open-loop 이 맞지만, 이번 목적("목표의 몇 배까지 버티나")에는 현재 모델로 충분했다.

### 다음 단계: open-loop 스트레스 테스트 (예정)

**VU 증설은 기각했다.** closed-loop 에서 VU 는 5초에 1번만 쏘고 나머지 시간은 잠들어 있는데,
그 잠자는 VU 수천 개를 유지하는 비용은 생성기가 전부 낸다. 1500 VU 에서 이미 k6 CPU 가 2% 대로
올라왔으므로 5000 VU 면 **생성기가 서버보다 먼저 병목이 되어 측정이 오염된다.**

바꿀 것은 VU 수가 아니라 부하의 모양이다. `constant-arrival-rate` 로 초당 요청수를 직접 지정하면
응답이 7ms 이므로 VU 1명이 초당 약 140 요청을 낸다. **VU 100명 남짓으로 1000 RPS 이상**이 나온다.
더 정확하면서 동시에 더 싸다.

측정 단위가 바뀐다는 점에 주의한다. 이번 결과는 "동시 시청자 몇 명까지" 로 읽지만, open-loop 결과는
**"이 엔드포인트가 초당 몇 요청까지 받는가"** 다. 사용자 수로 환산하려면 5 를 곱한다(진행률 저장이
5초 주기이므로 진행률 저장 1000 RPS = 시청자 5000명분). 이 환산은 요청 비중을 지금과 같게
유지할 때만 성립한다.

| 항목 | 계획 |
|---|---|
| 부하 | 500 → 1000 → 2000 → 4000 RPS, 각 2분 |
| 중단 조건 | 에러율 1% 초과 또는 p95 가 SLO(500ms) 초과 시 자동 중단 |
| 첫 병목 예상 | DB 커넥션 풀(20개, 이번 측정에서 최대 4개 사용) |
| 볼 것 | 한계 RPS 뿐 아니라 **무너지는 방식** — 느려지며 버티는지(graceful) 한 번에 무너지는지(cliff) |
| 주의 | 이번엔 실제로 깨질 수 있다. 운영 DB 와 같은 호스트라 실사용자도 영향을 받는다. 저트래픽 시간대에 돌릴 것 |

기존 `slo`·`knee` 시나리오와 임계값은 그대로 두고 `TEST=stress` 를 새로 붙인다(비교 가능성 유지).

### 판정: 포화점은 약 1,200 RPS, 최대 처리량은 약 1,440 RPS

**1,200 RPS 까지는 요청을 늘린 만큼 처리량이 따라 올라갔다.** 968 → 1,190 → 1,378 RPS 로 오르는 동안
p50 은 7.1 → 8.4 → 10.5ms 로 거의 그대로였다.

**그 위에서는 처리량이 1,300~1,440 RPS 에 갇힌 채 지연만 올라갔다.** 요청을 두 배로 늘려도(목표
1000 이터레이션/초 = 약 1,400 RPS 요구) 처리량은 더 오르지 않고 p50 이 10ms → 393ms 로 39배가 됐다.
**처리량 정체 + 지연 급증**, 정확히 포화점의 정의다.

| 구분 | 값 |
|---|---|
| 안전 운영 한계 | 약 **1,200 RPS** (p95 63ms, SLO 500ms 대비 여유) |
| 포화 시작 | 약 **1,300 RPS** |
| 최대 처리량 | 약 **1,440 RPS** (단 p50 이 100ms 를 넘어 실사용 불가) |

동시 시청자로 환산하면(진행률 저장이 전체의 72%, 시청자 1명당 5초에 1회):
1,200 RPS × 0.72 ÷ 0.2 = **약 4,300명**. 목표 부하 500명의 8.6배다.

이 환산은 앞선 knee 측정과도 맞아떨어진다. 1500명 → 진행률 저장 300 RPS ÷ 0.72 = 417 RPS 로,
실측 416.5 RPS 와 일치한다. 두 측정이 서로를 검증한다.

### 무너지는 방식: cliff 가 아니라 graceful

**에러가 단 한 건도 없었다(253,644 요청 중 0).** 커넥션 거부도, 5xx 도, 타임아웃도 없었다.
한계를 넘겨도 요청을 떨어뜨리지 않고 **느려지면서 전부 처리했다.**

운영 관점에서 이게 중요한 이유는 대응 시간이 있다는 뜻이기 때문이다. 한 번에 무너지는(cliff)
시스템은 오토스케일이 반응하기 전에 이미 장애지만, 이 경우 지연 상승이 먼저 관측되므로
알람 → 증설의 시간이 확보된다.

| 서버측 평균 응답 | 71.8ms | 84.6ms | — |

**커넥션 20개가 전부 사용 중이고 스레드 170여 개가 줄을 서 있었다.** knee 측정에서 최대 4개만
쓰이던 그 풀이다. 지연의 대부분은 쿼리 자체가 아니라 **커넥션을 기다린 시간**이다.

다만 JVM CPU 도 99.9% 라 커넥션 풀만 키우면 해결된다고 단정할 수 없다. 풀을 늘리면 동시 쿼리가
늘어 Postgres 쪽으로 병목이 옮겨갈 수 있고, 이 호스트는 12코어를 Postgres·Redis·Kafka 와
나눠 쓰고 있다. **다음 개선은 풀 크기 상향 후 재측정으로 확인해야 한다.**

생성기는 병목이 아니었다: k6 CPU 최대 5.37%, 호스트 CPU 최대 78%.

### 측정 방법에서 걸린 함정 (2회 실패)

두 번은 서버 한계가 아니라 **테스트 방식 때문에** 중단됐다. 같은 실수를 반복하지 않도록 남긴다.

| 시도 | 증상 | 원인 |
|---|---|---|
| 1차 | 30초 만에 중단, p95 18.77s | 1,711 요청 중 1,132 건이 로그인. VU 가 2000 까지 폭주 |
| 2차 | 4분 08초에 중단, VU 8 → 600 | 10초 만에 로그인 278 건. 붕괴 지점이 워밍업 뒤로 밀렸을 뿐 |
| 3차 | 정상 측정 | 로그인을 `setup()` 으로 이동 |

원인은 하나다. open-loop 은 목표 발생률을 맞추려고 VU 를 동적으로 늘리는데, **VU 가 새로 생길 때마다
로그인(BCrypt)을 하면 되먹임이 생긴다.** 서버가 느려짐 → k6 가 VU 증설 → 새 VU 마다 BCrypt →
CPU 고갈 → 더 느려짐. closed-loop(`knee`)에서는 VU 가 1분에 걸쳐 천천히 늘어 로그인이 분산되므로
드러나지 않던 문제다.

**해결: 인증은 측정 대상이 아니라 준비물이므로 `setup()` 에서 세션 200개를 미리 받아 두고 VU 가
빌려 쓴다.** 부하 구간에는 로그인 요청이 0건이다. 3차 실행에서 VU 1명이 89 이터레이션/초를 낸 것이
이 효과다(1차에서는 VU 2000명이 그보다 적게 냈다).

이 사실 자체도 정보다. **동시 로그인 폭주는 이 시스템에서 가장 먼저 무너지는 지점이다.**
배포 직후 세션이 한꺼번에 만료돼 재로그인이 몰리는 상황이 실제로 이에 해당한다. 별도 시나리오로
측정할 가치가 있다(미측정).

### 남은 이상 징후 (미규명)

500 이터레이션/초 유지 구간(경과 90~210s, 약 695 RPS)에서 두 번 순간 정지가 있었다.
경과 160s 에 p95 2,032ms, 경과 200s 에 p95 6,962ms 다. 전후 구간은 p95 9ms 로 정상이고
처리량도 유지됐다. p99 가 3,375ms 인 것도 이 두 구간 때문이다.

포화와는 무관한(그 시점 부하는 한계의 절반) 산발적 정지이며, GC 오버헤드가 0.6% 라 GC 도 아니다.
**원인 미규명.** 락 경합이나 커넥션 재생성이 의심되지만 확인하지 않았다.

## 개선 후 재측정 (Redis write-back) — 2026-07-27

같은 시나리오를 다시 돌렸다. 요청 경로에서는 Redis 에만 쓰고, 스케줄러가 10 초마다 버퍼를 통째로
들어내 배치 upsert 한다.

| 항목 | 값 |
|---|---|
| 대상 이미지 | `ghcr.io/kimgyuhyun/ott-backend:cc126d2…` |

### 판정: 포화점 1,200 → 약 1,840 RPS

| 구분 | 개선 전 | 개선 후 | 배수 |
|---|---|---|---|
| 안전 운영 한계 | 1,200 RPS | 약 **1,840 RPS** | 1.5배 |
| 최대 관측 처리량 | 1,440 RPS | 약 **2,240 RPS** | 1.6배 |
| 동시 시청자 환산 | 약 4,300명 | 약 **6,600명** | 1.5배 |
| 에러 | 0 / 253,644 | 0 / 909,084 | — |

환산식은 `RPS × 진행률저장 비중(0.72) × 저장주기(5초)` 다. 1,840 × 0.72 × 5 ≈ 6,600.
**주기와 비중이 지금 시나리오와 같을 때만 성립한다** — 프론트의 저장 주기가 바뀌면 인원도 같이 바뀐다.

무너지는 방식은 여전히 graceful 이다. 909,084 요청 중 에러 0 건, 지연만 올라갔다.

### 병목이 커넥션 풀에서 CPU 로 옮겨갔다

| 지표 | 1,390 RPS 구간 | 포화 구간(약 2,000 RPS) |
|---|---|---|
| JVM CPU | 87% | **100%** |
| 커넥션 사용/풀 | 1~2 / 20 | 19.4 / 20 (평균) |
| 대기 스레드 | 0 | 68 (평균) |

포화 구간에서는 풀이 다시 찬다. 다만 이건 원인이 아니라 결과로 보인다 — CPU 가 100% 라 커넥션을
쥔 스레드가 CPU 차례를 못 받아 점유 시간이 늘어난다. **1,390 RPS 에서 CPU 는 이미 87% 인데
커넥션은 1~2 개뿐**이라는 게 근거다. 따라서 다음 개선 대상은 풀 크기가 아니라 CPU 다.

다만 **CPU 개선은 실익이 없다고 판단해 여기서 멈췄다.** 목표 부하 500명의 13배까지 나왔으므로
더 늘려야 할 이유가 없다. 필요해지면 무엇이 CPU 를 쓰는지 먼저 재고 나서 손대야 한다.

## 한계

- **절대 RPS 는 이 호스트에서만 유효하다.** 다른 사양에 그대로 적용할 수 없다.
- 결과 2 는 측정 경로에서 **nginx 와 TLS 가 빠져 있다.** 엣지 구간의 비용은 포함되지 않았다.
  포화점 측정도 같은 경로라 동일하게 적용된다.
- 생성기가 같은 호스트에서 돌았다. CPU 기록으로 병목이 아님은 확인했으나 이상적인 구성은 아니다.
- closed-loop `knee` 측정은 **1500 VU 까지만 확인했고 거기서 꺾이지 않았다.** 한계는 그 뒤의
  open-loop `stress` 측정에서 잡았다(개선 전 약 1,200 RPS, 개선 후 약 1,840 RPS).
- 개선 전 `stress` 측정은 **2000·4000 이터레이션/초 계단까지 가지 못하고 중단됐다.** 중단 조건이 먼저
  걸렸기 때문이며 의도된 동작이다. 개선 후 측정도 생성기의 maxVUs 600 에 걸렸으므로, 두 측정의
  최대 처리량은 모두 "관측된 최대"이지 "낼 수 있는 최대"가 아니다.
- `stress` 는 세션 200개를 VU 들이 공유한다. 실사용자는 세션이 전부 다르므로 **세션 조회 캐시가
  실제보다 유리하게 작동했을 수 있다.**
- 병목을 DB 커넥션 풀로 지목했으나 JVM CPU 도 동시에 100% 였다. **풀만 키우면 해결된다는 것은
  검증되지 않았다.**
- 계단별 수치는 k6 의 원시 시계열(`--out csv`)을 유지 구간으로 잘라 다시 계산한 값이다.
  k6 요약이 직접 출력한 값이 아니다.

**최대 관측 처리량은 오르지 않았다.** 개선 전 3,087 RPS, 개선 후 2,910 RPS 로 오히려 5.7% 낮다.
다만 이것을 "느려졌다" 로 읽으면 안 된다. **같은 이미지인 1회차와 3회차 사이의 차이가 3,179 대
2,910 으로 8.5%** 라, 회차 간 편차가 두 이미지의 차이보다 크다. 즉 **차이를 분간할 수 없다.**

커넥션 풀은 이전 측정과 같은 모습이다. 500·1000 단계에서 사용 최대 0~3 / 20, 대기 0. 포화 단계
(2000·4000)에서만 20 / 20 이 되고 대기 스레드가 89~135 로 쌓인다. 이건 원인이 아니라 결과다 —
CPU 가 99% 라 커넥션을 쥔 스레드가 차례를 못 받는다.

### 같은 부하대의 CPU: 8% 낮게 나왔지만 유의하다고 말할 수 없다

포화 단계는 양쪽 다 CPU 가 99% 에 붙어 비교가 안 된다. 여유가 있는 1,500 RPS 구간으로 본다.

| 회차 | RPS | JVM CPU | RPS 당 CPU |
|---|---|---|---|
| 2 (개선 전) | 1,506 | 71.2% | 0.0473 |
| 3 (개선 후) | 1,529 | 66.6% | **0.0435** (-8.0%) |
| 1 (개선 후, 예열됨) | 1,484 | 67.3% | 0.0453 |

개선 후가 낮게 나왔지만, **같은 이미지인 1·3 회차 사이에도 4.1% 편차가 있다.** 8% 는 그 두 배일
뿐이고 회차가 3개뿐이라 유의성을 주장할 수 없다. **"내려간 것으로 보이나 확정하지 못했다"** 가
이 측정이 말할 수 있는 전부다.

주의: 여기서 JVM CPU 100% 는 호스트 12코어가 아니라 **컨테이너에 걸린 `cpus: 2.0` 상한**이다.
백엔드 두 대의 합계 4코어가 이 구성의 천장이다.

### 왜 안 움직였나

제거된 조회의 **DB 실행시간 총합이 24.4초**다(개선 전 회차, 1,012,387건). 부하 구간 633초로
나누면 코어 하나의 3.9%, 호출 1건당 0.024ms 다. 병목은 이전 측정에서 확인한 대로 CPU 이고,
그 CPU 는 백엔드 컨테이너의 2코어 상한이다. **요청당 0.024ms 짜리 DB 왕복을 없앤 것으로는
그 천장이 움직이지 않는다.**

병목은 옮겨가지 않았다. 여전히 CPU 다.

### 이 측정이 답하지 못하는 것

- **쓰기 API 경로를 재지 못했다.** `9a4c01b`(`getReferenceById`)의 효과는 찜·댓글·리뷰·별점 같은
  쓰기 API 에서만 나타나는데 `main.js` 에는 쓰기 요청이 하나도 없다(진행률 저장·목록·상세·재생URL
  4종뿐). 개선 전 회차의 `pg_stat_statements` 에 id 기준 users 조회가 아예 없다는 것이 그 증거다.
  **이 변경의 효과는 이번 측정에서 0 으로 보이며, 그것은 효과가 없다는 뜻이 아니라 측정하지 않았다는
  뜻이다.** 재려면 시나리오에 쓰기 요청을 넣어야 하고, 그건 이번 작업 범위 밖이다.
- **최대 처리량은 여전히 "관측된 최대"다.** 세 회차 모두 k6 의 `maxVUs` 600 에 걸려 이터레이션을
  26~28만 건 흘렸다. 목표 4000 이터레이션/초를 채운 회차가 없다.
- **생성기와 서버가 같은 호스트에서 경쟁했다.** k6 컨테이너 CPU 는 평균 0.7코어 / 최대 1.7코어였고
  호스트 전체 CPU 는 최대 90~100% 에 닿았다. 백엔드가 각자 2코어 상한에 붙어 있었으므로 서버가
  포화했다는 판정 자체는 유효하지만, 이상적인 구성은 아니다.
- **회차가 3개뿐이라 통계적 유의성이 없다.** 위의 CPU 8% 와 처리량 5.7% 는 모두 회차 간 편차와
  같은 크기다. 확정하려면 같은 조건을 여러 번 반복해야 한다.
- **2회차만 배경 작업이 하나 적다.** `0ac115b`(정기결제 스윕 스케줄러, 프로덕션 30분 주기)가
  개선 후 이미지에만 있다. 요청 경로와 무관하지만 완전히 동일한 조건은 아니다.
- 이전 측정과 마찬가지로 **nginx 와 TLS 가 빠진 경로**이고, 세션 200개를 VU 들이 공유한다.

## HikariCP connection-timeout 실측 조정 — 2026-08-13

`application-prod.yml` 의 `connection-timeout` 은 설정 파일 초기 커밋(`814c25e`)부터 30000ms 였다.
튜닝한 값이 아니라 HikariCP 기본값 그대로다. 같은 블록에서 `maximum-pool-size`(20)와
`minimum-idle`(5)만 기본값과 다르고 `connection-timeout` / `idle-timeout` / `max-lifetime` 셋은
기본값과 정확히 일치한다.

이 값은 "DB 에 접속하는 시간 제한" 이 아니라 **풀에서 빈 커넥션을 받을 때까지 스레드가 대기하는
최대 시간** 이다.

### 왜 줄이려 했나

Redis write-back 이후 진행률 저장(트래픽의 72%)은 요청 경로에서 DB 를 쓰지 않는다. 원리상 DB 가
죽어도 72% 는 서비스할 수 있다. 그런데 타임아웃이 30초면 DB 를 쓰는 28% 가 톰캣 스레드를 30초씩
붙잡아 200개를 고갈시키고, **살릴 수 있던 72% 까지 같이 죽는다.** 빨리 실패해서 스레드를 회수하는
쪽이 낫다.

### 합격 기준 (측정 전에 적음)

| 관측된 acquire 최대 | 정할 값 |
|---|---|
| 1초 미만 | 3000ms |
| 1초 이상 | 10000ms |
| 메트릭이 없거나 구간 만료 | 바꾸지 않고 근거만 주석으로 남김 |

### 관측 범위

Prometheus `storageRetention` 은 15일(기본값, 플래그 미설정)이고 실제 최초 샘플은
2026-07-29 07:00 UTC 다. **2026-07-27 측정 구간은 이미 만료됐고**, 2026-08-12 측정은 남아 있다.
아래는 8/12 세 회차 전체(19:40~23:10 KST)를 인스턴스별로 집계한 것이다.

### 결과

| 항목 | ott-app | ott-app-2 |
|---|---|---|
| acquire 최대 | **3.585s** | 1.208s |
| acquire 평균 (`_sum`/`_count`) | 0.020s | 0.0199s |
| acquire 호출수 | 2,273,095 | 2,235,718 |
| pending 최대 | 135 | 122 |
| `connections_timeout_total` | 0 | 0 |

최대가 나온 19:45 구간의 15초 간격 스냅샷은 `active` 20 / `idle` 0 / `pending` 63~121 이다.
풀이 완전히 포화된 실제 획득 대기이고 재기동 직후가 아니다(`process_uptime_seconds` 연속).
회차별 최대는 3.585 / 1.200 / 0.887초였다. 포화 버스트 5분만 잘라도 평균은 0.033초다.

**앞서 이 문서가 적은 "대기 1초 미만"은 틀렸다.** 그것은 응답 p95 에서 추론한 값이고 직접 측정한
것이 아니었다. 평균은 20ms 로 추론과 맞지만 꼬리가 180배 길다.

### 판정

관측 최대 3.585초 ≥ 1초 → **10000ms**. `application-prod.yml` 에 적용하고 근거를 주석 한 줄로
남겼다. 3.585초 대비 2.8배 여유다.

`connections_timeout_total` 이 0 인 것은 여유가 있다는 뜻이 아니라 30초라서 발동한 적이 없다는
뜻이다. 10초 적용 후에는 이 지표가 실제 신호가 된다.

### 부하시험을 다시 돌리지 않은 이유

타임아웃은 처리량이 아니라 **실패하는 방식**을 바꾼다. 같은 부하를 다시 걸면 최대가 또 3.5초쯤
나올 것이고 10초에 걸리지 않아 결과가 같다. 이 변경의 목적(DB 장애 시 72% 생존)은 부하시험이
아니라 **DB 정지 드릴**로만 확인되며, 그것은 아직 하지 않았다.

### 곁가지: acquire 14초 이벤트의 정체

보존 기간 안에 `acquire_seconds_max` 가 14초를 넘은 지점이 두 번 있다.

| 시각(KST) | 인스턴스 | acquire | creation | pending | active |
|---|---|---|---|---|---|
| 07-31 05:30 | ott-app-2 | 14.153s | 4.004s | 0 | 0 |
| 08-02 20:20 | ott-app-2 | 14.137s | 3.965s | 0 | 0 |

**풀 경합이 아니다.** 대기 스레드 0, 활성 커넥션 0 인데 획득이 14초 걸렸고 같은 스크레이프에
커넥션 생성 4초가 찍혔다. Loki 로그가 원인을 말해준다.

```
Failed to validate connection org.postgresql.jdbc.PgConnection@...
(This connection has been closed.). Possibly consider using a shorter maxLifetime value.
```

풀에 있던 커넥션이 **DB 쪽에서 끊긴** 것이다. 수명 만료가 아니라 상대가 닫았다. 전 기간에서 이
경고는 5개 시점에만 나오고 매번 두 인스턴스에 함께 나타난다.

| 시각(KST) | 그 시각에 있었던 일 |
|---|---|
| 07-31 03:26 | `9fe2e8b` 컨테이너 보안 설정 전면 적용 (03:32 커밋) |
| 07-31 04:22 | `301abd2` 전 컨테이너 CPU/메모리 상한 (04:31 커밋) |
| 08-02 20:19 | `9b25840` 설정 마운트 이동 (20:07 커밋) |
| 08-02 20:30 | **`ott-postgres` 컨테이너 재생성 시각과 초 단위로 일치** |
| 08-08 03:32 | 미확인 |

`docker inspect ott-postgres` 의 `Created` 가 `2026-08-02T11:30:21Z`(= 08-02 20:30 KST)로 네 번째
줄과 맞는다. 즉 **컨테이너를 재생성하는 인프라 변경 배포 중에 postgres 가 새로 뜨면서 풀의 커넥션이
끊겼고**, 그다음 요청이 죽은 커넥션을 골라내고 새로 만드느라 기다린 것이다.

호스트 절전은 아니다. Windows Kernel-Power 이벤트는 조회 구간에 08-04 22:33 한 번뿐이고 위
시각들과 겹치지 않는다.

### 그래서 14초는 문제인가

| 항목 | 관측 |
|---|---|
| 빈도 | 15일 중 2회 |
| 상황 | 둘 다 컨테이너를 재생성하는 인프라 배포 중 |
| 정상 트래픽·부하시험 중 발생 | 0회 |
| 발생한 에러 | 0건 (30초가 흡수) |
| 영향 요청 수 | 유휴 시간대(초당 0.35 획득)라 1~2건 추정 |

**상시 결함이 아니라 계획된 재생성 배포의 일시 현상으로 판정한다.** 다만 타임아웃을 10초로 내렸으므로
같은 일이 재발하면 이제는 에러로 드러난다. 그 대가는 배포 중 요청 1~2건이고, 롤링 배포가 이미 502 를
내는 것을 감안하면 받아들일 만하다.

없애려면 `keepaliveTime` 을 켜서 하우스키퍼가 유휴 커넥션을 미리 확인하게 하면 된다. 죽은 커넥션
정리가 요청 경로 밖으로 빠진다. **이번에는 넣지 않았다** — 관측된 빈도가 낮고, 넣으면 검증도 같이
해야 한다.

### 이 조사가 답하지 못한 것

- **7/27 의 "남은 이상 징후"는 여전히 미규명이다.** 위 14초 이벤트는 배포 중 postgres 재생성이
  원인이라 성격이 다르다. 그 정지는 배포 없이 부하시험 도중에 났고, 해당 구간 지표는 retention
  만료로 사라졌다. 락 경합 가설도 그대로 남아 있다.
- **`ott-app-2` 에 쏠린 이유를 모른다.** 검증 실패는 양쪽에 나오는데 14초 획득은 두 번 다
  `ott-app-2` 에서만 났다. 표본이 2개라 우연과 구분할 수 없다.
- **10초가 충분한지는 아직 이 값으로 잰 실측이 아니다.** 근거는 30초 설정에서 관측된 3.585초다.
  다음 부하시험에서 `connections_timeout_total` 을 함께 봐야 확정된다.
