### 결과 1: nginx 경유 — 측정 실패

목표 부하를 만들지 못했다. **서버 문제가 아니라 레이트 리밋에 막힌 것**이다.

| 지표 | 값 |
|---|---|
| 실패율 | **72.70%** (38,058 / 52,349) |
| 로그인 실패율 | 77.27% (1,700 / 2,200) |
| 처리량 | 115.2 RPS (시도 기준) |

실패 응답은 전부 nginx 가 백엔드에 보내지 않고 돌려준 것이다. `docker logs ott-nginx` 의
`limiting requests` 기록이 38,059 건으로 k6 가 센 실패 38,058 건과 일치했다.

원인은 `limit_req` 가 `$binary_remote_addr` 기준이라 VU 500 명이 IP 한 개의 버킷(general 30 r/s)을
공유한 것. 실사용자 500 명이면 IP 가 흩어져 발생하지 않는다. 자세한 내용은 README 의 레이트 리밋 절.

이 구간의 지연 수치(p95 14ms 등)는 **리밋을 통과한 26% 에 대한 값이라 성능 지표로 쓸 수 없다.**

### 판정: 1500 VU 까지 꺾이지 않았다

포화점의 정의는 **처리량이 정체되는데 p95 만 급격히 올라가는 지점**이다. 둘 다 나타나지 않았다.

- 처리량은 VU 에 정비례했다. VU 1명당 RPS 가 0.278 / 0.276 / 0.274 / 0.277 / 0.278 로 계단 내내 평평하다.
  정체 구간이 없다 = 서버가 요청을 밀어내지 못한 순간이 없었다.
- p95 는 10ms 안팎에 머물렀다. 1500 VU 에서 12.86ms 로 올라갔지만 100 VU 의 11.69ms 와 같은 급이고,
  급격한 상승이 아니다. p99 만 18 → 29ms 로 조금 벌어졌다.
- 에러 0 건(163,117 요청 중 0), 로그인 실패 0 건(1,500 중 0).
- `iteration_duration` 중앙값 5.00s = 설계값 그대로. **이터레이션이 밀리지 않았다** — 밀리기 시작하면
  VU 가 다음 tick 을 제때 못 쏘므로 처리량 정체로 먼저 드러난다. 그 조짐이 없었다.

즉 **이 호스트에서는 1500 VU(동시 시청자 1500명, 416 RPS)까지 여유가 있다.** 목표 부하 500명의 3배다.

### 이 측정이 답하지 못하는 것

**한계를 찾지 못한 이유는 서버가 무한히 빨라서가 아니라, 이 부하 모델이 요청량을 스스로 제한하기 때문이다.**
VU 1명은 5초에 1 tick 이라는 고정 주기로 돌기 때문에(closed-loop) 서버가 아무리 빨라도 1500 VU 가
만들 수 있는 부하는 약 417 RPS 가 상한이다. 실제로 그 상한이 그대로 나왔다. 즉 이번에 확인한 것은
"416 RPS 까지는 확실히 여유"이지 "한계가 416 RPS"가 아니다.

진짜 포화점을 보려면 둘 중 하나가 필요하다.

| 방법 | 내용 |
|---|---|
| VU 를 더 올린다 | 3000 ~ 5000 VU. 계정 500개를 6~10 세션이 공유하게 된다 |
| open-loop 로 바꾼다 | `constant-arrival-rate` 로 목표 RPS 를 직접 지정. 서버가 느려져도 요청 발생률이 안 줄어 큐가 쌓이는 게 보인다 |

closed-loop 은 서버가 느려지면 부하도 같이 줄어들어 포화를 완만하게 감춘다. 한계를 정확히 재려면
open-loop 이 맞지만, 이번 목적("목표의 몇 배까지 버티나")에는 현재 모델로 충분했다.

### 다음 단계: open-loop 스트레스 테스트 (예정)

**VU 증설은 기각했다.** closed-loop 에서 VU 는 5초에 1번만 쏘고 나머지 시간은 잠들어 있는데,
그 잠자는 VU 수천 개를 유지하는 비용은 생성기가 전부 낸다. 1500 VU 에서 이미 k6 CPU 가 2% 대로
올라왔으므로 5000 VU 면 **생성기가 서버보다 먼저 병목이 되어 측정이 오염된다.**

바꿀 것은 VU 수가 아니라 부하의 모양이다. `constant-arrival-rate` 로 초당 요청수를 직접 지정하면
응답이 7ms 이므로 VU 1명이 초당 약 140 요청을 낸다. **VU 100명 남짓으로 1000 RPS 이상**이 나온다.
더 정확하면서 동시에 더 싸다.

측정 단위가 바뀐다는 점에 주의한다. 이번 결과는 "동시 시청자 몇 명까지" 로 읽지만, open-loop 결과는
**"이 엔드포인트가 초당 몇 요청까지 받는가"** 다. 사용자 수로 환산하려면 5 를 곱한다(진행률 저장이
5초 주기이므로 진행률 저장 1000 RPS = 시청자 5000명분). 이 환산은 요청 비중을 지금과 같게
유지할 때만 성립한다.

| 항목 | 계획 |
|---|---|
| 부하 | 500 → 1000 → 2000 → 4000 RPS, 각 2분 |
| 중단 조건 | 에러율 1% 초과 또는 p95 가 SLO(500ms) 초과 시 자동 중단 |
| 첫 병목 예상 | DB 커넥션 풀(20개, 이번 측정에서 최대 4개 사용) |
| 볼 것 | 한계 RPS 뿐 아니라 **무너지는 방식** — 느려지며 버티는지(graceful) 한 번에 무너지는지(cliff) |
| 주의 | 이번엔 실제로 깨질 수 있다. 운영 DB 와 같은 호스트라 실사용자도 영향을 받는다. 저트래픽 시간대에 돌릴 것 |

기존 `slo`·`knee` 시나리오와 임계값은 그대로 두고 `TEST=stress` 를 새로 붙인다(비교 가능성 유지).

## 한계

- **절대 RPS 는 이 호스트에서만 유효하다.** 다른 사양에 그대로 적용할 수 없다.
- 결과 2 는 측정 경로에서 **nginx 와 TLS 가 빠져 있다.** 엣지 구간의 비용은 포함되지 않았다.
  포화점 측정도 같은 경로라 동일하게 적용된다.
- 생성기가 같은 호스트에서 돌았다. CPU 기록으로 병목이 아님은 확인했으나 이상적인 구성은 아니다.
- 포화점 측정은 **1500 VU 까지만 확인했고 거기서 꺾이지 않았다.** 한계값 자체는 여전히 모른다
  (위의 "답하지 못하는 것" 참고).
- 계단별 수치는 k6 의 원시 시계열(`--out csv`)을 유지 구간으로 잘라 다시 계산한 값이다.
  k6 요약이 직접 출력한 값이 아니다.
